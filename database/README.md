# Database

This folder contains the SQL schema and a sample data dump for the SQLite
database that backs the application. The files here can be used to spin up a
local database from scratch, to inspect the schema without running the .NET
project, or to reset the database to a known state during development.

## Files

| File                   | Description                                                   |
| ---------------------- | ------------------------------------------------------------- |
| `schema.sql`           | The `CREATE TABLE` statement and indexes only.                |
| `workorders-dump.sql`  | The schema together with fifteen sample work order records.   |
| `README.md`            | This document.                                                |

## Schema overview

The application uses a single SQLite database file named `workorders.db`,
which lives next to the backend project at runtime. There is one table:
`WorkOrders`. The schema is generated by Entity Framework Core directly
from the `WorkOrder` C# model class, so the column names match the model
properties one-to-one.

```
+-------------------------------------------+
|                WorkOrders                 |
+-------------------------------------------+
| PK  Id                INTEGER             |
|     WorkOrderNumber   TEXT      NOT NULL  |
|     Title             TEXT      NOT NULL  |
|     Description       TEXT      NULL      |
|     Priority          TEXT      NOT NULL  |
|     Status            TEXT      NOT NULL  |
|     CustomerName      TEXT      NOT NULL  |
|     TechnicianName    TEXT      NULL      |
|     EstimatedCost     TEXT      NULL      |
|     CreatedAt         TEXT      NOT NULL  |
|     UpdatedAt         TEXT      NOT NULL  |
+-------------------------------------------+
```

## Column reference

| Column             | Type     | Required | Notes                                                                                          |
| ------------------ | -------- | -------- | ---------------------------------------------------------------------------------------------- |
| `Id`               | INTEGER  | Yes      | Auto-incrementing primary key.                                                                 |
| `WorkOrderNumber`  | TEXT     | Yes      | Human-readable identifier. Generated by the API as `WO-yyyyMMdd-XXXX` on insert.               |
| `Title`            | TEXT     | Yes      | Short summary of the job, shown in the list view.                                              |
| `Description`      | TEXT     | No       | Free-form details about the request.                                                           |
| `Priority`         | TEXT     | Yes      | One of: `Low`, `Medium`, `High`.                                                               |
| `Status`           | TEXT     | Yes      | One of: `New`, `Assigned`, `In Progress`, `On Hold`, `Completed`, `Cancelled`.                 |
| `CustomerName`     | TEXT     | Yes      | The facility or building the work order belongs to.                                            |
| `TechnicianName`   | TEXT     | No       | The assigned technician, if one has been chosen.                                               |
| `EstimatedCost`    | TEXT     | No       | A decimal value stored as text. This is how Entity Framework Core represents decimals on SQLite. |
| `CreatedAt`        | TEXT     | Yes      | ISO 8601 UTC timestamp. Set when the record is first created and never changed afterwards.     |
| `UpdatedAt`        | TEXT     | Yes      | ISO 8601 UTC timestamp. Refreshed every time the record is edited.                             |

## Design notes

The application is intentionally focused on one resource — the work order
itself — so the schema is kept deliberately simple. A natural next step
would be to break `CustomerName` and `TechnicianName` out into their own
`Customers` and `Technicians` tables and join them in through foreign keys,
along with separate tables for parts, labor entries, and attachments.

## Working with the dump

If you have the `sqlite3` command-line tool installed, you can rebuild and
explore the database in a few commands:

```bash
# Build a fresh database from the dump
sqlite3 workorders.db < workorders-dump.sql

# Look at the schema
sqlite3 workorders.db ".schema WorkOrders"

# Browse the seed data
sqlite3 workorders.db "SELECT Id, WorkOrderNumber, Title, Status, Priority FROM WorkOrders;"

# Count records by status
sqlite3 workorders.db "SELECT Status, COUNT(*) FROM WorkOrders GROUP BY Status;"
```

The dump file also opens cleanly in
[DB Browser for SQLite](https://sqlitebrowser.org/) or the SQLite extension
for VS Code.

## API endpoints that read and write this table

| HTTP verb and route               | What it does                                                              |
| --------------------------------- | ------------------------------------------------------------------------- |
| `GET /api/workorders`             | Lists work orders, with optional `status`, `priority`, and `search` query parameters. |
| `GET /api/workorders/{id}`        | Returns a single work order by its primary key.                           |
| `GET /api/workorders/stats`       | Returns aggregate counts for the dashboard cards.                         |
| `POST /api/workorders`            | Creates a new work order and auto-generates its `WorkOrderNumber`.        |
| `PUT /api/workorders/{id}`        | Updates a work order, preserving `Id`, `WorkOrderNumber`, and `CreatedAt`. |
| `DELETE /api/workorders/{id}`     | Removes a work order from the table.                                      |
